## 2. The migrations

Six files, in order. Each was dry-run against live inside a rolled-back
transaction and returned no error.

**131 — the SMS claim batch size.** Written earlier, never applied.

**133 — the admin escalation.** `fn_guard_verification_verdicts` recreated in
full with a `role` clause. Permits exactly `tenant -> owner`, which is what
`SupabaseAuthService.becomeHost()` writes from the client, and refuses
everything else. `admin` is unreachable from a client in either direction.

**134 — the listing-images bucket.** All three write policies were
`bucket_id = 'listing-images'` and nothing else. Now: INSERT requires
`can_upload_listing_image()`, UPDATE and DELETE require the object's own
`owner` (or an admin).

Two decisions inside it are worth knowing about.

*Ownership is the `owner` column, not the path.* The obvious rule — "the first
folder must be a listing you own" — refuses every first publish, because
`CreateListingScreen` uploads photos before the listing row exists, under a
synthetic `listing_<millis>` folder. On live, 12 of 42 objects sit under a
real listing uuid and 30 do not. `owner` is populated on all 42.

*Uploading is deliberately easier than publishing.* Publishing is the
predicate the `listings` INSERT policy already used — verified owner or admin
— now extracted into `can_publish_listings()` so the two cannot drift.
Uploading is that **or you already own a listing**, because live has 4
listings belonging to 2 accounts that predate migration 114 and could not
publish today. They can still edit those listings, so the strict rule would
have let them change everything about a listing except its photos.

**135 — booking sanity.** A host cannot book their own listing; a booking
cannot start more than an hour in the past. INSERT-time only, so the one
self-booking already on live is left alone. The hour of slack is deliberate:
booking a turf for *this* hour is the normal case for an hourly listing.

**136 — payment attempts and risk.** Adds `abandoned` and `pending_review`
to the payment states, a 15-minute sweep that closes `initiated` rows over an
hour old, and `admin_release_payment` / `admin_reject_payment`. Live is
carrying 27 stale `initiated` rows worth ৳52,420 that the sweep will close on
its first run.

**137 — the admin UPDATE policy on `bookings`.** One policy, the same shape
`listings_admin_update` already had.

## 3. The failure mode worth repeating

The console's refund switch did nothing for as long as the screen has existed,
and nobody saw an error, because **PostgREST does not refuse an UPDATE whose
rows RLS filtered out.** It succeeds, changes nothing, and returns an empty
set. The action's "no rows changed" branch then reported *"Only a paid booking
can be marked refunded"* however paid the booking was.

The same trap produced four false results in the first draft of the QA
capability matrix. Every write test in the new suite reads a probe value
before and after rather than watching for an exception.

## 4. Payments

`sslcommerz-ipn` had two faults and they compounded.

It sent `type: "paymentReceived"`; the enum has `payment_received`. Postgres
refused it, the insert sat inside a `try`, and the error was swallowed — so
**every online payment on live notified nobody**, 12 of them, while the 3 cash
notifications worked and made the gap invisible. Fixed, and the failure is now
logged with the payload rather than discarded.

It also settled risk-flagged payments. SSLCommerz marks an otherwise VALID
transaction with `risk_level` non-zero when its fraud screen fires, and its
guidance is to hold before delivering. Such a payment is now `pending_review`
and **the booking stays unpaid** — that is the half that matters; the payment
row is bookkeeping. The guest is told their money arrived and is being
checked, every admin gets an alert, and the console's new **Held** tab
releases or rejects it through the two service-role RPCs.

`sslcommerz-init` closes this booking's earlier open attempts before creating
another, and refuses after six in an hour.

## 5. Everything else

**The migration chain (F5) is decided.** 003 contained SQL that was never
valid — a `UNIQUE` constraint over `LEAST`/`GREATEST` expressions, which only
an index may do — so `supabase start` stopped dead there. That is repaired.
With it repaired, all 137 files were replayed into an empty database: **103
applied, 34 failed.** Some failures are the minimal scaffold rather than the
repo, but eight migrations from 062 onward need `listings.max_guests`, three
need `bookings.listing_title`, and others need `listings.city`,
`facilities.code` and `facilities.icon` — **columns that exist on live and
that no file in the repo adds.** Pieces of the chain were never committed, so
repairing it means writing DDL nobody has. `supabase/migrations/README.md`
records the decision: the baseline is the build, the chain is history.

**Test 093** resolved three live uuids by hand and errored on any other
database. It now finds its own subjects, prefers a listing that already has an
address row so it still tests real data on live, and seeds one otherwise. It
also asks for a *live* entitlement rather than any completed booking — the
`completed` grace is seven days from `ends_at`, so a months-old stay correctly
discloses nothing and would have read as a broken test. All nine rows match
their documented expectations on the local mirror.

**The edge functions** all type-check now. The one that mattered:
`messenger-webhook` called `.catch()` on a `PostgrestFilterBuilder`, which is
a thenable with no such method, so the best-effort analytics guard was a
runtime `TypeError`. All nine `supabase-js` imports are pinned to 2.45.4, and
CI has a Deno job that runs `deno check` over all thirteen.

**Accessibility.** Six control families gained names: the search button, the
wishlist hearts, the account menu, the notification bell, the leaderboard
trophy and the brand. The trap is that **a `Tooltip` does not name a
control** — it sets the semantic *tooltip* and leaves `label` empty — and
nearly every one of these already had one. The E2E strategy in `qa-plan.md`
selects by accessibility label, so this unblocks that too.

**Concurrency.** One retry on `40P01` / `40001`, and a second failure renders
as "this time slot was just booked by someone else" rather than a generic
banner. Once, not a loop: the race is already decided by the time the retry
runs.
