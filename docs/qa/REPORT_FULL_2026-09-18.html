4. The other three capability failures

Any signed-in user can overwrite any listing image S2

Why
The storage policy is using (bucket_id = 'listing-images') with no owner clause. Measured: another host changed the object's metadata to {"hacked": true}. Deleting is refused, but only by Supabase's own protect trigger, and overwriting defaces just as well.
Fix
Tie the object path to the listing's owner, the way the avatars policy ties a filename to the user's id.

Any signed-in user can upload into that public bucket S3

Why
The insert policy checks only the bucket name. A guest who hosts nothing can upload 5 MB images with no rate limit in front of it.

A host can book their own listing, and anyone can book the past S3

Self-booking
The booking function never compares the listing's owner to the caller, so a host can post earnings to themselves.
Past dates
No past-date guard exists server-side. A booking starting ten days ago was accepted and returned an id. Past slots are always free, so availability never objects, and the auto-complete sweep marks it done at once. The calendar hides past dates, which is the "form is not enforcement" pattern again.

Almost nothing is labelled for a screen reader S3

Measured
With the accessibility tree switched on, 38 nodes exist and 8 carry a label: the two section headings and the six listing cards. The search pill's three segments, Filters, the search and voice buttons, the wishlist hearts, the account menu and the bottom navigation have a role but no name.
Two costs
A screen reader user hears "button" with no idea what it does. And the end-to-end plan, which selects controls by accessibility label, cannot address most of the interface. One Semantics(label: …) per control fixes both.

Signed-out visitors trigger a failing request on every launch S4

What
The device watcher runs at startup and on every resume without checking for a session, so touch_device is called with no user and refused. It is caught and fails open, but it is a red 401 on every visit and will fill error tracking once that exists.

6. What this round proved is working

  • Cross-user isolation holds everywhere tested except the two storage policies above. Bookings, payments, payout methods, notifications, favourites, identity documents and profile fields are invisible to strangers, by policy rather than by the app.
  • Identity verification really gates publishing and booking, from the database.
  • Migration 132 holds both ways: neither guest nor host can stamp a booking paid, while cash and gateway settlement still work.
  • The state machine refuses every wrong actor: a guest cannot accept, a host cannot touch another host's reservations, a stranger cannot cancel.
  • Under genuine contention no slot was ever double-booked.
  • Every lifecycle transition notifies the right person.
  • Reviews stay double-blind until revealed.
