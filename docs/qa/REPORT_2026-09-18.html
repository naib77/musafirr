2. The migrations do not rebuild the database

First thing tried: supabase start on an empty Docker database, which applies supabase/migrations 001 to 132 in order. It stopped at 003.

Applying migration 001_initial_schema.sql...
Applying migration 002_notifications.sql...

  CONSTRAINT unique_conversation UNIQUE (
    LEAST(participant_one_id, participant_two_id),

A UNIQUE constraint cannot contain expressions in any Postgres version. So this file was never applied to live as written. Live has a unique index of that shape and a text column with a check instead of the enum 003 declares. The repo does not hold the SQL live was actually built from.

Found while reading this function · Online payments never notify anyone F2 · S2

What
On success the function inserts a notification with type: "paymentReceived". The enum has payment_received. The insert throws, the try/catch swallows it, and settlement proceeds.
Proof, local
insert into notifications (…, type, …) values (…, 'paymentReceived', …);
ERROR: invalid input value for enum notification_type: "paymentReceived"
Proof, live
12 online payments are paid; 0 notifications came from them. The 3 payment_received rows that exist all came from cash confirmations, which use the correct spelling.
Effect
Guest's Trips does not update live after paying; host never gets "you can now mark the service complete".

F11 · A risky payment is settled like a clean one S3

What
SSLCommerz sets risk_level 1 when its fraud screen fires and advises holding delivery. The IPN accepts any VALID/VALIDATED answer and only stores the risk fields, so a risky payment unlocks Service complete and posts the host's earning immediately.
Decide
hold as pending review with an admin notification, or accept knowingly and record it.

Observation · Host response window on live is 1 hour

What
booking_accept_window_hours = 1 on live, set by an admin 2026-09-09. The local cron rejected a fixture booking after an hour, exactly as configured. Not a bug; confirm it is intended.

8. Other probes on the mirror

Master OTP login, the path the Play reviewer and QA use works as documented

How

POST /functions/v1/verify-otp  {"phone":"01700000003","otp":"0000"}
→ {"success":false,"error":"No active code. Please request a new one."}
Reads as
A wrong code falls through to the normal path and finds no row, without counting an attempt. That is the documented "master path is unthrottled" behaviour; locally it is harmless, on production it is why the secrets should be unset after each review.

Admin console "Mark refunded" exactly as the console sends it F3 · S2

How
PATCH /rest/v1/bookings?id=eq.bbbbbbbb-…-0002&payment_status=eq.paid
Authorization: Bearer <admin JWT>
Prefer: return=representation
{"payment_status":"refunded"}

Why
bookings has UPDATE policies for the host and the tenant only. An admin's JWT matches neither, so PostgREST updates zero rows and returns an empty list. The console then shows "Only a paid booking can be marked refunded" for a booking that is paid. Same result expected on live; fix belongs in ../musafir-admin (service-role client or an admin_* RPC).

10. What was not tested, and why

  • Server-to-server IPN. The sandbox cannot reach localhost, so only the browser-redirect settlement was observed. The IPN-and-redirect race needs a tunnel (cloudflared or ngrok) in front of the local gateway.
  • The Flutter payment screens and the Android WebView return. The mirror is ready for an app build pointed at 127.0.0.1:54321; this is where /flutter-add-integration-test and Playwright come in.
  • Production smoke with the master account and ৳10. Deliberately last, after the above pass locally; runbook in docs/qa/payment-test-plan.md section 3.
