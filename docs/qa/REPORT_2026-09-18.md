## 2. What was built to make this possible

The plan assumed a staging database built from `supabase/migrations`. That
is not possible today: `supabase start` on a fresh database fails at
migration 003, whose `UNIQUE (LEAST(a,b), GREATEST(a,b))` is not valid
Postgres and never was. Live has a unique *index* of that shape instead, and
its `conversations.status` is text with a check, not the enum 003 declares.
So the chain in the repo is not the chain live came from, and CLAUDE.md's
warning that live has drifted is an understatement: from 003 onward the
repo cannot rebuild live.

Live cannot be dumped with `pg_dump` either: the `SUPABASE_DB_URL` value the
secrets API returns is a SHA-256, not a connection string, and there is no
database password on this machine. The only read path is the Management
API, so:

- `tool/dump_live_baseline.py` reads the live catalog through that API and
  writes `supabase/baseline/live_baseline.sql`: 10 enums, 42 tables, 70
  foreign keys, 144 functions, 6 views with their options, 75 indexes, 95
  policies, 59 triggers including the `auth.users` signup hook, exact
  grants for `anon`/`authenticated`/`service_role` including the one
  column-level grant, and 8 cron jobs. Every statement is idempotent.
- `tool/local_db_from_live.sh` applies it repeatedly until the failure
  count stops shrinking (dependency order settles by itself), loads the
  reference rows (`app_settings`, `facilities`, `landmarks`, `app_secrets`
  keys with placeholder values), applies the migrations newer than live
  (131, 132), then the synthetic seed.
- `supabase/baseline/qa_seed.sql`: six synthetic accounts (two hosts, a
  verified and an unverified guest, an admin, one with no usable phone),
  four listings including a ৳10-per-hour seat and a turf, six bookings
  covering every status, one paid payment. No real person or listing.
- `supabase/config.toml` (new, local): migrations and seed disabled with a
  comment saying why. `supabase/functions/.env.local` (ignored): sandbox
  gateway URL, placeholder store credentials, a local master OTP list.

Parity check, local versus live, same query on both: 43 tables, 144
functions, 95 policies, 59 triggers, 8 views, 133 indexes, 42 RLS tables,
8 cron jobs, 95 SECURITY DEFINER functions, 523 anon column SELECT grants.
Identical on all ten.

Gaps in the mirror: storage policies (15 on live) and `auth` configuration
are not dumped; `app_secrets` values are placeholders; the `auth.users` rows
are synthetic so the legacy-identity resolution in `verify-otp` is exercised
only against seed accounts.

### S1

**F1. A guest or host can mark their own booking paid with one PATCH.**
Confirmed on live (rolled back) and reproduced locally through PostgREST
with a guest JWT. Migration 132 plus `supabase/tests/132_*` are written;

### S2

**F2. Online payments never notify anyone.** `sslcommerz-ipn` inserts
`type: "paymentReceived"`; the enum has `payment_received`. The insert
fails inside a try/catch and is swallowed. Live: 12 online paid payments,
0 notifications from them (the 3 that exist are cash). Locally:
`invalid input value for enum notification_type: "paymentReceived"`. The
guest's Trips does not update live and the host never gets "you can now
mark the service complete". One-word fix in the function, plus a test row
that walks the enum.

**F3. The admin console's "Mark refunded" is a no-op.** `bookings` has
UPDATE policies for host and tenant only. The console PATCHes with the
admin's JWT; PostgREST returns `[]`, the row stays `paid`, and the action
reports "Only a paid booking can be marked refunded". Reproduced locally
with the seeded admin. Fix in `../musafir-admin`: use the service-role
client that already exists in `lib/supabase/server.ts`, or an `admin_*`
RPC. This is also why 132 is a trigger guard rather than a column revoke.

### S3

**F4. `sslcommerz-init` has no cap per booking.** Six rapid calls made six
more `payments` rows for one booking (seven total). Live carries 27
`initiated` rows worth ৳52,420 from July and August that nothing expires.
Fix: refuse or reuse when an `initiated` row younger than N minutes exists,
and a sweep marking older `initiated` rows `abandoned`.

**F5. The migration chain does not apply from scratch** (section 2). Every
future staging or local database depends on the baseline tool until the
chain is repaired or officially replaced by a baseline plus forward
migrations from 131.

**F6. Test 093 hardcodes live ids** (`9c5181a0…`, the real "cozy room 1")
and errors on any other database. Rewrite against fixtures like 113 to 132.

**F7. Three edge functions fail `deno check`** (`messenger-webhook`,
`whatsapp-webhook`, `validate-discount`): `SupabaseClient` generic drift
from `esm.sh/@supabase/supabase-js@2` resolving to whatever is newest. Pin
the version in all 13 imports; add `deno check` to CI.

Two more findings from this run:

**F11 (S3). `risk_level = 1` is settled as paid.** SSLCommerz marks a
validated transaction risky (`risk_level 1`, `risk_title` set) when its fraud
screen fires; its own guidance is to hold such a payment for review before
delivering. `sslcommerz-ipn` accepts `VALID`/`VALIDATED` and ignores the risk
fields beyond storing them, so a risky payment unlocks Service complete and
posts the host's earning at once. Decide: hold as `pending_review` and notify
admin, or accept and record the decision.

**Observation. The host response window on live is 1 hour**, set by an admin
on 2026-09-09 (`booking_accept_window_hours = 1`; the seed default was 24).
Not a bug; the cron did exactly what the setting says and rejected a fixture
booking after an hour. Worth confirming that is intended, since a host who is
asleep loses every request.

**Observation. `verify-otp` rotates the user's password on every login**, by
design (it destroys the old phone-derived passwords). Logging a seeded account
in through the master OTP therefore breaks its `qa-password`; reset with
`update auth.users set encrypted_password = crypt('qa-password', gen_salt('bf'))`.
Noted in `supabase/baseline/qa_seed.sql`.
