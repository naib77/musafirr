The pattern behind most of it

Thirty-odd of these findings are one bug in different clothes: a rule the app enforced and the database did not. The booking form checked capacity, the Dart lifecycle service checked state transitions, the client filtered blocked users, the widget hid past dates. Every one of those is skippable, because the REST layer is a public endpoint and the compiled-in key is in the web bundle. The fix each time was to move the rule into a trigger, a policy or the RPC, and to pin it with a test that goes red when the rule is removed.

The second pattern is quieter and produced the false “everything passes” of the first drafts: an UPDATE whose rows row-level security filters out matches nothing and raises nothing. PostgREST answers 200 with an empty list. The console's refund button had been inert since it shipped for exactly this reason, and four rows of the first capability matrix passed for the same reason. Every write test now reads a value before and after.

What mattered most

Six of the 53, chosen for what a guest or host would have called them: theft, spying, or the app lying about money.

N1S1On live

Anyone signed in could make themselves an admin

One request with the key that ships in the web bundle and your own login turned a guest into an administrator with access to every booking, payment, identity document and exact address. Proved on the production database inside a rolled-back transaction.

Now · Migration 133 permits exactly the “become a host” move and refuses every other role change. Applied 19 Sep; re-verified on live afterwards.

F1S1On live

A guest could mark their own booking paid

One PATCH set the payment status. The host's earning was posted for money that never moved.

Now · Migration 132 guards the settlement columns for anyone who is not an admin or the payment gateway. Applied 18 Sep.

Q41S1Function not redeployed

Paying after a cancellation marked the cancelled booking paid

A guest opened the bank page, the booking was cancelled while it was open, the guest completed payment. Driven for real on the SSLCommerz sandbox: the cancelled booking became paid and the host got an earning.

Now · The settlement decision is a pure function with its own tests. Such a payment is held, the booking stays unpaid, the admin is told to refund and cannot release it by mistake.

Q14S1Written, not on live

A host could rewrite a booking's history

Cancelled back to confirmed, rejected back to confirmed, completed with no check-in. The whole state machine lived in the app; the database accepted any transition from the listing owner.

Now · Migration 138 holds the state table in a trigger. Terminal states are terminal, which also ends the accept-after-cancel race.

Q8S2Written, not on live

Either participant could swap the other out of a conversation

A guest replaced the host with a stranger in one request. The stranger read the entire history; the host lost the thread.

Now · Migration 138 freezes participant ids for anyone who is not an admin.

Q44S2Written, not on live

Live realtime never fired for bookings

The app subscribes to bookings and the subscription reports active, but the production publication does not include the table. Hosts saw new requests only through the notification row.

Now · Migration 138 adds bookings to the publication. This one is a production configuration fact, not a code fault.

How we tested

The plan assumed a staging database built from the repo's migrations. That was not possible: migration 003 contains SQL that was never valid, and even with it repaired, 34 of the 137 files fail because live carries columns that no file adds. Live cannot be dumped either; there is no database password on this machine. So the first day built the environment everything else ran on.

The environment

  • A local mirror built from the live catalogue. tool/dump_live_baseline.py reads every enum, table, function, view, policy, trigger, grant and cron job through the Management API; tool/local_db_from_live.sh applies it until stable, loads reference rows, applies the migrations newer than live, then a synthetic seed. Checked identical to live on tables, functions, policies, triggers, views, indexes, RLS, cron, definers and grants.
  • A synthetic cast standing in for 80 guests and 50 hosts. Two hosts (a seat and a room; a turf and a hidden house), a verified guest, an unverified guest, eight racer guests, an admin, and an account with no usable phone. No real person or listing. Every scenario names who acted.
  • The real SSLCommerz sandbox. The owner registered a sandbox store; credentials live only in an ignored env file. A headless-Chromium driver (tool/qa/sandbox_pay.js) walks the bank page for Success, Success with risk, Failed and Cancel and rewrites the redirect so settlement lands on the local stack.
  • Live, read-only or rolled back. Two findings were confirmed on the production database inside transactions that were rolled back. Every migration was dry-run there the same way before it was applied.

Two rules every write test follows

  1. Measure the effect, never the exception. Read a value, attempt the write as the impersonated user, read again, report CHANGED, NO-OP or REFUSED with the SQL state and hint.
  2. Clear the JWT claims when dropping back to postgres. A stale subject leaves the guards refusing even the superuser, which reads as the fix being broken.

What was not tested

  • The server-to-server IPN from SSLCommerz cannot reach a laptop; the browser redirect path is what settled locally. Both paths run the same code.
  • A genuinely fraud-flagged gateway transaction cannot be summoned on demand. The hold is verified at the database level and by one sandbox run that happened to return a risk flag.
  • The Flutter payment screens and the Android WebView return were not driven end to end; the functions they call were.
  • No real login was automated: the OTP path sends a real SMS. The seeded numbers use the local master code only.

What held

A findings list reads as if nothing works. Much of it does, and was measured to.

  • Cross-user isolation holds everywhere tested except the two storage policies fixed in 134: bookings, payments, payout methods, notifications, favourites, identity documents and profile fields are invisible to strangers by policy, not by the app.
  • Identity verification genuinely gates publishing and booking from the database.
  • No slot was ever double-booked: exactly one booking survived every race at 2, 3, 4 and 8 concurrent guests across 11 runs. The exclusion constraint does the work.
  • Every lifecycle transition notified the right party: request, accept, cash confirmation, check-in, completion, both reviews, and a stranger seeing none of them.
  • The payment refusal matrix: 17 init and IPN cases all answered as specified, including a forged validation id, a replayed genuine one, and a real validation id attached to a different transaction.
  • Live reconciliation: 15 paid bookings, 15 paid payments, 0 orphans either way, ৳13,610.
  • Signed-out browsing: listings, facilities and amenity search work; profiles, bookings and exact addresses are refused outright.
  • The interface renders at 1440, 1000 and 390 px with no sideways scroll.
  • Daily and monthly pricing at Dhaka midnight counts nights and months correctly across month and year boundaries.

Ship list

Every remaining step is a production action. In this order.

  1. Apply migration 138 to live

    Through the Management API, dry-run in a rolled-back transaction first, as the earlier six were. Then run 138_qa_round2_test.sql against live, rolled back, and check bookings appears in the realtime publication.

    139 adds an enum label and Postgres will not let 140 use it in the same transaction (55P04). Not reversible. Then 139_140_open_items_test.sql rolled back on live.

Lessons for the next round

  • PostgREST answers 200 [] to a refused update. Measure the row, not the status code. The smoke harness keeps one row that exists only to show this.
  • The SQL suites do not roll themselves back. Run them through run_sql_tests.sh. An hour was lost to fixtures a previous run had committed, and the mirror's settings held junk values (whenever, lots) from a suite that proves fallbacks by writing junk.
  • A Tooltip does not name a control. It sets the semantic tooltip and leaves the label empty; the end-to-end strategy selects by label.
  • Trigger order is alphabetical by name, and 140 depends on it: the guard runs before the refund stamp. Rename either and check.
  • An enum label is a two-file migration and cannot be rolled back; the rolled-back-transaction safety net does not exist for it.
  • Local Storage stamps owner_id; live stamps owner. Every ownership policy checks both.
  • The sandbox returns a risk flag at random on identical successful runs. A held sandbox payment is not a bug.
  • A negative test proves nothing until the subject is proved negative. The first live re-check picked “a guest” who turned out to own two listings and read as a failed fix.
  • Notification timestamps are transaction time inside a test, so a wall-clock watermark matches nothing; track ids.
